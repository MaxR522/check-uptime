## Go concepts and idioms

### `:=` inside a block creates a new variable (shadowing)

`:=` declares a new variable in the current block. If a variable with the same name exists in an outer block, the new one hides it until the block ends. The outer one is not changed.

```go
func f(err error) {
    if err != nil {
        body, err := io.ReadAll(r) // NEW err, hides the parameter
        if err != nil { return }
        use(err.Error())           // this err is the inner one, and it is nil here: panic
    }
}
```

How to avoid it: give the second error its own name (`readErr`), or restructure so each error is handled where it happens. The gopls `nilness` analyzer flags it in the editor ("nil dereference in dynamic method call"). Plain `go vet` does not run `nilness`, so trust the editor warning.

The same trap exists with names other than `err`:

- A variable named like a function (`fullURL, err := fullURL(...)`) hides the function for the rest of the block.
- A parameter named like a package (`url string`) hides the `net/url` package inside the function.

### Calling a method on a nil interface panics

`err` is an interface. If it is nil, `err.Error()` has no concrete value to call the method on, and the program panics. Always check `err != nil` before calling methods on it.

### Failure is data, not a Go error

In a monitor, a site being down is a normal outcome. It belongs in the result, not in a Go `error` return. Keep `error` returns for problems with the program itself (the DB is down, bad config). Returning both the result and an error, then ignoring the error with `_`, was a sign that the design was mixing the two.

```go
func checkEndpoint(ctx context.Context, client *http.Client, target string) checkResult
```

### Build the result step by step, with early returns

Create the result once and fill in fields as you learn them. Return early on each failure. Fields you don't set keep their zero values (`nil`, `0`, `""`), so you don't need `id: 0` or `errorBody: nil`.

```go
result := checkResult{checkedAt: start}
// ...
if err != nil {
    result.errMsg = new(err.Error())
    return result
}
```

This replaced a helper that took `(resp, err)` and rebuilt the state with nested `if`s. That version ended up with 5 near-identical struct literals. The function that already knows its state should fill the result itself.

### `new(expr)` (Go 1.26)

Since Go 1.26, `new` accepts an expression and returns a pointer to a copy of it: `new(err.Error())` returns a `*string`. Before 1.26 you needed a helper, or a variable and `&v`.

### Slices: `len` vs `cap`

A slice has a length (the elements in use) and a capacity (the space in the underlying array). `s[:n]`:

- panics if `n > cap(s)`: "slice bounds out of range [:1048576] with capacity 512";
- does not panic if `len(s) < n <= cap(s)`, but returns bytes past the real data (garbage).

To cut to at most `n` elements, use the built-in `min` (Go 1.21):

```go
s = s[:min(len(s), n)]
```

### Don't abort a whole loop because of one item

In a loop over many independent items (websites, endpoints), `return err` on one bad item skips all the others. Log the error and `continue`. Check `ctx.Err()` in long loops so shutdown stops the work quickly.

### Timing

Capture `start := time.Now()` once. Use it for the timestamp (`checkedAt: start`) and for the duration (`time.Since(start)`). Calling `time.Now()` again at the end gives the end time, not the start. Measure the duration after reading the body if "response time" should include the download.

### Two different limits

- **Read limit**: how much to load into memory (`1 << 20`, 1 MB). It must be big enough for later assertions like `body_contains`.
- **Storage limit**: how much to keep in the DB (`250` bytes for `errorBody`).

One constant cannot serve both purposes. Cutting a string at a byte can split a multi-byte UTF-8 character. `strings.ToValidUTF8` can clean the result if needed.

## Standard library behavior that mattered

### `http.Client.Do`

- `err != nil` only for transport failures: DNS, connection refused, TLS, timeout, redirect policy.
- When `err != nil`, `resp` is nil, except when `CheckRedirect` fails, and then its body is already closed. Never touch `resp` on the error path.
- A 404 or 500 is not an error: `err == nil` and `resp.StatusCode == 500`. The error page body arrives on the success path.
- The client follows up to 10 redirects by default, so `StatusCode` is the status of the final page. Set `CheckRedirect` to return `http.ErrUseLastResponse` to see the 301/302 instead.

### Reading the response body

```go
defer resp.Body.Close()
body, err := io.ReadAll(io.LimitReader(resp.Body, maxBodyBytes))
```

- `resp.Body` is a stream. Read it once, then close it.
- `io.LimitReader` protects memory from huge or never-ending bodies.
- A read error (the connection dropped mid-body) is a real check failure. Record it, don't drop it.
- A body not read to the end prevents connection reuse. `io.Copy(io.Discard, resp.Body)` drains the rest.

### `url.JoinPath`

It joins a base URL and path segments. It escapes `?`, so a path like `/search?q=x` becomes `/search%3Fq=x`. If paths can contain a query string, parse the base and set `Path` and `RawQuery` yourself. Calling `url.Parse` on its result is redundant.

## Naming and style (Go Code Review Comments)

- Initialisms stay all-caps: `baseURL`, `fullURL`, `websiteID`, `endpointID`. Not `baseUrl` or `website_id`.
- No snake_case, no `SCREAMING_CASE`. Constants are normal Go names: `const maxBodyBytes = 1 << 20`.
- Use `const`, not an exported `var`, for fixed values. Any package can change an exported `var`.
- Name a type for one value in the singular: `checkResult`, not `checkResults`.
- Avoid field and variable names that collide with builtins or packages (`error`, `url`).
- Error messages: lowercase, no "error" prefix, include the inputs, wrap with `%w`: `fmt.Errorf("join %q and %q: %w", baseURL, path, err)`.
- `fmt.Println(err)` is enough. `.Error()` is not needed.

## Mistakes from today, and how to spot them

| Mistake | Why it was wrong | Spot it next time |
| --- | --- | --- |
| `return err` on one bad URL in the loop | skipped every other endpoint | in a loop over independent items, ask: should this stop everything? |
| Printed the error but forgot `continue` | ran a check on an empty URL | after handling an error in a loop, the next line should be `continue` or `return` |
| `body, err := ...` inside an `if err != nil` block | new `err` shadowed the parameter, which led to a nil method call | a `:=` with `err` inside a block that already has an `err` |
| Read `resp.Body` when `client.Do` failed | `resp` is nil there, so the program panics on the first site that is down | on `Do` error, use only `err` |
| Expected the 500 body on the error path | HTTP 500 is `err == nil` | status codes live on the success path |
| `errorBody` filled on 200s | stores useless data on every check | ask: when should this field be set? |
| A body read error returned an empty result | the failure was invisible | every early return should set the fields it already knows |
| `body[:maxBodyBytes]` | slicing past `len`/`cap` panics or returns garbage | `s[:n]` needs `n <= len(s)`; use `min` |
| `checkedAt: time.Now()` at the end | recorded the end time, not the start | capture `start` once and reuse it |
| `errMsg = nil` on a fresh struct | dead code | zero values are already set |

## Tools

- **gopls** (editor): the `nilness` analyzer caught the shadowed `err` before any review.
- **`go vet ./...`**: run it before every review. It does not include `nilness`.
- **`staticcheck`**: worth adding. It catches more bugs and style issues than `go vet`.
- **`httptest.NewServer`**: real HTTP tests without the network. The `body[:n]` panic would have shown up in the first 500 test.

## Self-review checklist (from today's mistakes)

Before asking for a review:

1. Is every error checked, and is every early return filling the fields it already knows?
2. Any `:=` inside a block that hides an outer variable (`err`, a function name, a package name)?
3. After `client.Do` fails, is `resp` left alone?
4. Is the body read with a limit, and is it closed?
5. Is every slice expression `s[:n]` safe when `len(s) < n`?
6. In loops: does one bad item stop everything? Is there a `continue` after logging?
7. Names: initialisms (`URL`, `ID`), no snake_case or SCREAMING_CASE, no shadowed packages.
8. Error messages: lowercase, with context, wrapped with `%w`.
9. Run `go vet ./...` and look at the editor warnings.
