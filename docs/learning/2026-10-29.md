## Concepts learned

### Two ways to make an HTTP request

`http.Get` is the simple way, but it uses `http.DefaultClient`, which has no timeout and cannot be cancelled. The idiomatic way builds the request with a context and sends it with your own client:

```go
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil {
    return err
}
resp, err := client.Do(req)
if err != nil {
    return err // errors.Is(err, context.DeadlineExceeded) works here
}
defer resp.Body.Close()
```

Why: the context controls the whole lifetime of the request, including reading the body, so cancelling a parent context (shutdown) stops every request in flight.

### `Client.Timeout` vs context timeout

Both apply; the shorter one wins. Keep `Client.Timeout` as a hard safety net, use the context for cancellation and per-call deadlines.

### Streams (`io.Reader`)

A stream is data read in order, piece by piece, once. `Read(p)` fills up to `len(p)` bytes, `n < len(p)` is normal, and `io.EOF` is the normal end signal. Readers compose: `io.LimitReader(resp.Body, max)` wraps one stream in another.

### Channels as a mental model for streams

A channel already behaves like a stream: in order, consumed once, blocking when empty, with an end signal (`close(ch)` ↔ `io.EOF`). Differences: a Reader gives byte chunks with meaningless boundaries, a channel gives whole typed values; channels are safe for concurrent use, Readers usually are not; the consumer closes a Reader, the sender closes a channel.

### Designing a concurrent function: make the signature answer the questions

From *Concurrency in Go* (Katherine Cox-Buday), chapter 1, "Determining Concurrency Safety". A concurrent function is hard to use correctly when its signature is ambiguous:

```go
// CalculatePi calculates digits of Pi between the begin and end place.
func CalculatePi(begin, end int64, pi *Pi)
```

The caller cannot tell: should I start goroutines myself? Who synchronizes access to `*Pi`?

Fix 1: a doc comment that answers three questions:

1. **Who** is responsible for the concurrency?
2. **How** is the problem mapped onto concurrency primitives?
3. **Who** is responsible for the synchronization?

Fix 2: let the signature carry the answer:

```go
func CalculatePi(begin, end int64) []uint      // no shared state: no synchronization question
func CalculatePi(begin, end int64) <-chan uint // returns a channel: the function starts its own goroutine(s)
```

Returning a receive-only channel says: "I own the concurrency. You only receive, and the channel is closed when I am done." The caller does not wrap the call in `go`, does not close the channel, and does not lock anything.

Applied in the project: `checkAllEndpoints` returns `(<-chan checkResult, error)`. The function starts the workers, owns the `WaitGroup`, and closes the channel; `RunChecker` only ranges over it. The `error` covers the synchronous part (loading websites) before any goroutine starts; per-endpoint failures travel inside each `checkResult`.

Trade-off from the book: clarity vs performance. They can coexist, but it gets harder as the team grows. Prefer clarity first.

### Fan-in with a WaitGroup: who closes the channel

Many workers send to one channel, one consumer ranges over it. The rules that make it correct:

- The **sender side** closes the channel, never the receiver.
- No single worker knows it is the last one, so a `sync.WaitGroup` counts them and **one owner** closes after `wg.Wait()`.
- `defer close(ch)` at the top of the owning goroutine closes the channel on every path, including early returns and panics.
- Each worker's send uses `select` with `case <-ctx.Done():` so a worker never blocks forever if the consumer is gone.
- Each value carries its own identity (`endpointID`), because results arrive in any order.

```go
go func() {
    defer close(out)
    var wg sync.WaitGroup
    for _, job := range jobs {
        wg.Go(func() { // Go 1.25+: Add(1) + go + Done() in one call
            select {
            case out <- process(job):
            case <-ctx.Done():
            }
        })
    }
    wg.Wait()
}()
```

## Lessons from mistakes

### `cancel` must run on every path

In the first version, the per-endpoint `cancel()` was only called inside `case <-ctx.Done():`. On the normal path it never ran, so each context kept its timer until the timeout fired.

Why it was wrong: a `context.WithTimeout` holds resources until it is cancelled or expires. Fix: `defer cancel()` at the top of the code that owns the context (here, inside the worker).

How to spot it next time: for every `WithTimeout` / `WithCancel`, trace each path and check `cancel` runs on it. `go vet`'s `lostcancel` check does **not** catch this case: it only fires when `cancel` is never used, and here it was used in one branch inside a closure.

### Results without identity

`checkResult` first had no endpoint id, so results from the channel could not be matched to their endpoint. With concurrency, order is lost, so each message must carry what it belongs to. The same applies to log output: `String()` should print the field too.

### Reusing a Client is not about avoiding re-initialization

The first idea was that reusing an `http.Client` avoids re-creating it on every `http.Get`. But `http.Get` already reuses a single package-level `DefaultClient`, and creating a Client is cheap. The connection pool lives in the **Transport**: a Client with a nil `Transport` uses the shared `http.DefaultTransport`.

How to spot it next time: ask "where does the expensive state live?" Here it is the Transport, so the trap is creating a new `http.Transport` per request, not a new Client. The real reasons for your own Client are configuration (timeout, redirect policy, transport), isolation from global state, and testability.

The first version of `http-client.md` also had this wrong ("a new Client per request loses the connection pool"); it was corrected the same day.

## Standard library APIs

- `http.NewRequestWithContext`: the context covers connection, sending, headers and body reading.
- `http.Client`: `Transport` nil means `DefaultTransport`. `Timeout` includes reading the body; the timer keeps running after `Do` returns.
- `http.Client.CheckRedirect` + `http.ErrUseLastResponse`: stop at the first response instead of following redirects.
- `io.Reader` / `io.Writer` / `io.Copy` / `io.LimitReader` / `io.Discard`.
- `io.Pipe`: connected Reader and Writer with a blocking hand-off between goroutines.

## Tools

- `go doc net/http.NewRequestWithContext` and `go doc net/http.Client` to read the docs from the terminal.
- `go vet` flags a `context.WithTimeout` whose `cancel` is never called.

## Self-review checklist

- [ ] Every HTTP call uses a client with a timeout, never `http.Get` / `http.DefaultClient`.
- [ ] Requests are built with `NewRequestWithContext` and the caller's context.
- [ ] `defer resp.Body.Close()` comes right after the `err` check.
- [ ] One `http.Client` per configuration, created once; no `http.Transport` created per request.
- [ ] Bodies from untrusted servers are wrapped in `io.LimitReader`.
- [ ] A stream is read only once; keep a `[]byte` if the data is needed again.
- [ ] Every `context.WithTimeout` / `WithCancel` has its `cancel` called on every path (`defer cancel()`).
- [ ] A function that starts goroutines says so: it returns `<-chan T`, or its doc comment answers who owns the concurrency and who synchronizes.
- [ ] The sender side closes a channel, once, after all senders are done (`WaitGroup` + `defer close`).
- [ ] Values sent through a channel carry their own identity.
